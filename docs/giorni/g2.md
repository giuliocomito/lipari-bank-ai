# Giorno 2: il contratto dell'API

[Torna al README](../../README.md)

Ogni mattina l'ufficio Operations carica l'estratto dei movimenti, e qualche riga è
sbagliata. Da questa giornata l'API classifica un movimento, importa il file intero
rendendo conto di ogni riga e riporta gli errori sempre nella stessa forma. Il codice
com'era alla consegna è nell'etichetta `g2`.

| endpoint | cosa fa |
|---|---|
| `POST /api/ai/categorize` | classifica un movimento (`description`, `amount` > 0, `currency` di tre lettere, EUR se manca) in una di sei categorie, con una `confidence` fra 0 e 1. Per ora decide una regola a parole chiave; dal Giorno 4 un modello, con lo stesso contratto |
| `POST /api/ai/movements/import` | un CSV (`multipart/form-data`, campo `file`, intestazione `date,description,amount,currency`, al massimo 2 MB): importa le righe valide e restituisce `imported_count` e `problems`, una voce per riga scartata con il suo numero nel file |
| `POST /api/ai/chat`, `POST /api/ai/glossary` | la chat (per ora un'eco) e il glossario interno |

Ogni errore, dal 404 al 500, ha la stessa busta: `timestamp`, `status`, `error` (il codice
stabile, per il programma), `message` (per una persona), `path` e `details` (per il 422,
un «campo: motivo» per campo). Il valore ricevuto non viene mai rimandato, e un 500 non
contiene traceback né percorsi di file.

## Le nove prove

Eseguite il 3 novembre 2026 dalla radice del progetto, a server acceso
(`uv run uvicorn src.main:app --reload`); gli esiti sono quelli osservati.

```bash
# 1. la chat risponde
curl -X POST localhost:8000/api/ai/chat -H "Content-Type: application/json" -d '{"session_id":"s-1","message":"Ciao"}'
# 2. una bolletta è riconosciuta, con la sua confidenza
curl -X POST localhost:8000/api/ai/categorize -H "Content-Type: application/json" -d '{"description":"Bonifico Enel Energia","amount":87.40}'
# 3. il mio identificativo di richiesta torna uguale
curl -i localhost:8000/health -H "X-Request-Id: ops-2026-0042"
# 5. un corpo invalido dice quale campo, nella busta
curl -X POST localhost:8000/api/ai/categorize -H "Content-Type: application/json" -d '{"description":"Esselunga","amount":-5,"currency":"euro"}'
# 6. nessun traceback: rotta che non c'è, metodo sbagliato
curl localhost:8000/non-esiste ; curl localhost:8000/api/ai/glossary
# 7. il CSV da duecento righe, sette sbagliate
curl -X POST localhost:8000/api/ai/movements/import -F "file=@examples/estratto-200.csv"
# 8. e 9. un file vuoto, un file che non è un CSV
curl -X POST localhost:8000/api/ai/movements/import -F "file=@vuoto.csv"
curl -X POST localhost:8000/api/ai/movements/import -F "file=@immagine.png"
```

| # | prova | esito |
|---|---|---|
| 1 | la chat risponde | `"reply":"Echo: Ciao"` |
| 2 | la bolletta | `UTILITIES` / `ENERGY`, `confidence` 0.8, «Parola chiave «enel».» |
| 3 | il request-id | `X-Request-Id: ops-2026-0042`, lo stesso che ho mandato |
| 4 | la pagina nel browser | `client/index.html` servita su `http://localhost:5173` (`uv run python -m http.server 5173 --directory client`): «Classifica» risponde 200 con la categoria |
| 5 | corpo invalido | 422, `VALIDATION_ERROR`, `details`: `amount: Input should be greater than 0`, `currency: String should match pattern…` |
| 6 | niente traceback | 404 e 405 nella busta; un JSON rotto dà `corpo: JSON decode error`; nel log del server, zero traceback |
| 7 | 200 righe, 7 sbagliate | `imported_count` 193, `problems` alle righe 12, 37, 58, 91, 120, 154, 188, ognuna con il suo motivo |
| 8 | file vuoto | 422 `INVALID_FILE` «Il file è vuoto»; il server risponde ancora |
| 9 | file non CSV | 422 `INVALID_FILE` «Il file non è testo UTF-8: non è un CSV» |

La pagina va aperta su `localhost` e non su `127.0.0.1`: per il browser sono due origini
diverse, e la seconda non è fra quelle ammesse dal CORS, come verifica
`test_cors_solo_per_le_origini_ammesse`.

Dal Giorno 3 la chat vuole `"new"` o una conversazione esistente, quindi oggi la prova 1,
con `"s-1"`, risponde 404 ([diario del Giorno 3](g3.md)).

## La demo di due minuti

1. Server e pagina accesi, `/docs` aperto: i quattro endpoint, con gli esempi di risposta.
2. Carico `examples/estratto-200.csv`: 193 righe importate, sette segnalate. Alla riga 58
   del file c'è `euro` al posto di `EUR`, come dice il motivo.
3. Lo ricarico: stesso esito, con `replayed: true`, e il conto non raddoppia.
4. Dalla pagina nel browser, «Bonifico Enel Energia»: `UTILITIES`, confidenza 0.8.

## La decisione: importare le righe valide e segnalare le altre

Su duecento righe, sette sbagliate, ho scelto di importare le 193 buone e restituire le
sette con numero di riga e motivo. Ho scartato il rifiuto del file intero: chi carica è un
ufficio che lavora un file al giorno, e respingerlo per una riga terrebbe fermi 193
movimenti giusti in attesa di chi prepara il file, mentre la correzione passa da un altro
sistema. La risposta dice invece che cosa fare subito, cioè correggere e ricaricare solo
quelle sette righe. Il conto torna sempre, perché `imported_count` più le voci di
`problems` dà il numero di righe di dati del file. Il rischio è che una riga sbagliata
passi per buona: i test lo coprono con dieci modi diversi di sporcare una riga, più le
sette del file d'esempio, e nessuna risulta importata.

## L'estensione n. 3: l'importazione rilanciabile

Lo stesso file caricato due volte non raddoppia il conto: la seconda volta torna l'esito
della prima, con `replayed: true`, e nulla viene ricontato.

Ho scelto di riconoscere «lo stesso file» dalla chiave che il chiamante dichiara
nell'header `Idempotency-Key`, come nei sistemi di pagamento, e in sua assenza dal
contenuto, byte per byte (sha256). La stessa chiave per un file diverso è un errore del
chiamante: 409 `IDEMPOTENCY_KEY_REUSED`, nella busta. Ho scartato il nome del file: ogni
mattina si chiama `estratto.csv`, quindi verrebbe rifiutato il file del giorno dopo,
mentre lo stesso file rinominato passerebbe due volte.

[`tests/test_import_rilanciabile.py`](../../tests/test_import_rilanciabile.py) carica due volte
`examples/estratto-200.csv` e il totale resta 193. Con una chiave, la stessa chiave e lo
stesso file restituiscono la prima risposta, la stessa chiave con un altro file 409, e il
totale non si muove.

Fino al database del Giorno 3 il registro sta in memoria e ricorda le ultime mille
importazioni. L'endpoint lo riceve con `Depends(get_registro)`, e per questo il test può
sostituirlo con uno vuoto (`dependency_overrides`). I limiti sono nella
[revisione](../ai-review/G2.md).
