# Giorno 2: il contratto dell'API

[Torna al README](../../README.md)

Ogni mattina l'ufficio Operations carica l'estratto dei movimenti, nel quale alcune righe
risultano errate. A partire da questa giornata l'API è in grado di classificare un singolo
movimento e di importare l'intero file rendendo conto dell'esito di ogni riga; inoltre
riporta gli errori sempre nella stessa forma. Il codice, nello stato in cui è stato
consegnato, è conservato nell'etichetta git `g2`.

| endpoint | funzione |
|---|---|
| `POST /api/ai/categorize` | Classifica un movimento, descritto da `description`, da `amount` (che deve essere maggiore di 0) e da `currency` (un codice di tre lettere, EUR se assente), in una di sei categorie, e restituisce una `confidence` compresa fra 0 e 1. Per ora la decisione è affidata a una regola basata su parole chiave; dal Giorno 4 sarà presa da un modello linguistico, con lo stesso contratto |
| `POST /api/ai/movements/import` | Riceve un CSV (`multipart/form-data`, campo `file`, intestazione `date,description,amount,currency`, dimensione massima di 2 MB), importa le righe valide e restituisce `imported_count` e `problems`, che contiene una voce per ciascuna riga scartata, con il relativo numero di riga nel file |
| `POST /api/ai/chat`, `POST /api/ai/glossary` | Espongono rispettivamente la chat, che per ora si limita a restituire il messaggio ricevuto, e il glossario interno |

Ogni errore, dal 404 al 500, viene restituito nella stessa busta, cioè in un oggetto JSON di
struttura fissa composto dai campi `timestamp`, `status`, `error` (il codice stabile,
destinato al programma chiamante), `message` (il testo destinato a una persona), `path` e
`details`. Per il 422, `details` contiene una voce nella forma «campo: motivo» per ciascun
campo errato. Il valore ricevuto nel campo errato non viene mai rimandato al chiamante, e
una risposta 500 non contiene né traceback né percorsi di file.

## Le nove prove

Le prove sono state eseguite il 3 novembre 2026 dalla radice del progetto, con il server in
esecuzione (`uv run uvicorn src.main:app --reload`); gli esiti riportati sono quelli
effettivamente osservati.

```bash
# 1. la chat risponde
curl -X POST localhost:8000/api/ai/chat -H "Content-Type: application/json" -d '{"session_id":"s-1","message":"Ciao"}'
# 2. una bolletta è riconosciuta, con la sua confidenza
curl -X POST localhost:8000/api/ai/categorize -H "Content-Type: application/json" -d '{"description":"Bonifico Enel Energia","amount":87.40}'
# 3. il mio identificativo di richiesta torna uguale
curl -i localhost:8000/health -H "X-Request-Id: ops-2026-0042"
# 5. un corpo invalido dice quale campo, nella busta
curl -X POST localhost:8000/api/ai/categorize -H "Content-Type: application/json" -d '{"description":"Esselunga","amount":-5,"currency":"euro"}'
# 6. nessun traceback: rotta che non c'è, metodo sbagliato
curl localhost:8000/non-esiste ; curl localhost:8000/api/ai/glossary
# 7. il CSV da duecento righe, sette sbagliate
curl -X POST localhost:8000/api/ai/movements/import -F "file=@examples/estratto-200.csv"
# 8. e 9. un file vuoto, un file che non è un CSV
curl -X POST localhost:8000/api/ai/movements/import -F "file=@vuoto.csv"
curl -X POST localhost:8000/api/ai/movements/import -F "file=@immagine.png"
```

| # | prova | esito |
|---|---|---|
| 1 | la chat risponde | La risposta contiene `"reply":"Echo: Ciao"` |
| 2 | la classificazione di una bolletta | Il movimento è classificato nella categoria `UTILITIES` / `ENERGY`, con `confidence` 0.8 e con la motivazione «Parola chiave «enel».» |
| 3 | l'identificativo della richiesta | La risposta riporta `X-Request-Id: ops-2026-0042`, lo stesso valore che ho inviato |
| 4 | la pagina nel browser | La pagina `client/index.html` è servita su `http://localhost:5173` (`uv run python -m http.server 5173 --directory client`); il pulsante «Classifica» riceve una risposta 200 con la categoria |
| 5 | un corpo non valido | Risposta 422 con codice `VALIDATION_ERROR` e, in `details`, le voci `amount: Input should be greater than 0` e `currency: String should match pattern…` |
| 6 | l'assenza di traceback | Le risposte 404 e 405 sono restituite nella busta; un JSON malformato produce `corpo: JSON decode error`; il log del server non contiene alcun traceback |
| 7 | un CSV di 200 righe, di cui 7 errate | Il campo `imported_count` vale 193, e `problems` segnala le righe 12, 37, 58, 91, 120, 154 e 188, ciascuna con il proprio motivo |
| 8 | un file vuoto | Risposta 422 `INVALID_FILE` con il messaggio «Il file è vuoto»; il server continua a rispondere |
| 9 | un file non CSV | Risposta 422 `INVALID_FILE` con il messaggio «Il file non è testo UTF-8: non è un CSV» |

La pagina deve essere aperta su `localhost` e non su `127.0.0.1`, perché il browser
considera i due indirizzi come origini diverse e la seconda non rientra fra quelle ammesse
dalla politica CORS, cioè dalle regole con cui il server indica al browser quali siti
possono chiamare l'API. Questo comportamento è verificato dal test
`test_cors_solo_per_le_origini_ammesse`.

A partire dal Giorno 3 la chat richiede il valore `"new"` oppure l'identificativo di una
conversazione esistente; per questo motivo la prova 1, che usa `"s-1"`, oggi riceve la
risposta 404 ([diario del Giorno 3](g3.md)).

## La dimostrazione in due minuti

1. Con il server e la pagina in esecuzione apro `/docs`, che mostra i quattro endpoint con
   gli esempi di risposta.
2. Carico `examples/estratto-200.csv`: vengono importate 193 righe e ne vengono segnalate
   sette. Alla riga 58 del file compare `euro` al posto di `EUR`, come indica il motivo.
3. Carico di nuovo lo stesso file: l'esito è identico, con `replayed: true`, e il conteggio
   non raddoppia.
4. Dalla pagina nel browser classifico «Bonifico Enel Energia», che ottiene la categoria
   `UTILITIES` con confidenza 0.8.

## La decisione: importare le righe valide e segnalare le altre

Su un file di duecento righe, di cui sette errate, ho scelto di importare le 193 righe
corrette e di restituire le sette errate con il numero di riga e il motivo del rifiuto. Ho
scartato l'alternativa di respingere l'intero file. Chi carica il file è infatti un ufficio
che ne elabora uno al giorno; respingerlo a causa di una sola riga bloccherebbe 193
movimenti corretti finché chi prepara il file, che lavora su un altro sistema, non lo avesse
corretto. La risposta indica invece che cosa fare subito, cioè correggere e ricaricare
soltanto quelle sette righe. Il conteggio risulta sempre coerente, perché la somma di
`imported_count` e del numero di voci di `problems` è uguale al numero di righe di dati del
file. Il rischio di questa scelta è che una riga errata venga accettata come valida. I test
coprono tale rischio con dieci modi diversi di alterare una riga, oltre alle sette righe
errate del file d'esempio, e nessuna di queste righe risulta importata.

## L'estensione n. 3: l'importazione rilanciabile

Se lo stesso file viene caricato due volte, il conteggio non raddoppia: al secondo
caricamento il servizio restituisce l'esito del primo, con `replayed: true`, e nessuna riga
viene conteggiata di nuovo.

Per stabilire se si tratta dello stesso file ho scelto di usare la chiave che il chiamante
dichiara nell'header `Idempotency-Key`, come avviene nei sistemi di pagamento; in assenza
della chiave, il riconoscimento si basa sul contenuto, confrontato byte per byte attraverso
l'impronta sha256. L'uso della stessa chiave per un file diverso è considerato un errore del
chiamante, che riceve nella busta la risposta 409 `IDEMPOTENCY_KEY_REUSED`. Ho scartato il
riconoscimento basato sul nome del file, perché il file si chiama `estratto.csv` ogni
mattina: con questo criterio verrebbe rifiutato il file del giorno successivo, mentre lo
stesso file, una volta rinominato, verrebbe importato due volte.

Il test [`tests/test_import_rilanciabile.py`](../../tests/test_import_rilanciabile.py)
carica due volte `examples/estratto-200.csv` e verifica che il totale resti 193. Quando la
richiesta contiene una chiave, il test controlla inoltre che la stessa chiave con lo stesso file restituisca la
prima risposta, che la stessa chiave con un file diverso produca un 409 e che in entrambi i
casi il totale rimanga invariato.

In questa giornata, in attesa del database introdotto nel Giorno 3, il registro delle
importazioni è conservato in memoria e ricorda le ultime mille importazioni. L'endpoint lo riceve tramite
`Depends(get_registro)`, cioè attraverso il meccanismo di iniezione delle dipendenze di
FastAPI; per questo il test può sostituirlo con un registro vuoto (`dependency_overrides`).
I limiti di questa soluzione sono descritti nella [revisione](../ai-review/G2.md).
